# Sparnarok: The Architect's Codex - Reglas de Contribución y Agente

## 1. Filosofía Central y Regla de Oro
> **"Ningún feature puede ser commiteado sin tests completos (Unit, Integration, E2E), cobertura total, y sin la documentación correspondiente (Swagger, TSDoc, XML comments o ADRs)."**

Esta regla es absoluta y de cumplimiento obligatorio para todas las iteraciones, desarrolladores y agentes en este proyecto.

## 2. Tech Stack Oficial
- **Backend:** .NET 10 Web API con C# y Entity Framework Core (PostgreSQL).
- **Frontend:** React 19+ con TypeScript, Vite y CSS modular/vanilla de alta fidelidad estética.
- **i18n:** Internacionalización nativa en ambos extremos (Backend: `Microsoft.Extensions.Localization`, Frontend: `react-i18next` o similar con soporte para español/inglés desde el día cero).
- **Testing:**
  - Backend: xUnit, Moq/NSubstitute, FluentAssertions y Testcontainers para PostgreSQL.
  - Frontend: Vitest + React Testing Library.
  - E2E: Playwright.
- **Documentación:**
  - OpenAPI / Swagger con soporte para XML Comments autogenerados.
  - TSDoc exhaustivo en interfaces, componentes y hooks de frontend.
  - ADRs (Architecture Decision Records) en formato Markdown bajo `/docs/adrs`.

## 3. Definición de Hecho (Definition of Done - DoD)
No se puede crear ningún commit o merge sin validar:
1. **Tests Unitarios:** Lógica matemática de simulación D&D 5e y componentes de UI testeados al 100% de caminos críticos.
2. **Tests de Integración:** Endpoints de API y persistencia en PostgreSQL validados con contenedores reales (Testcontainers).
3. **Tests End-to-End (E2E):** Flujos de usuario simulados mediante Playwright.
4. **Cero Fallos:** Toda la suite de tests debe ejecutarse y pasar localmente y en CI.
5. **Cumplimiento i18n:** Prohibido cadenas de texto estáticas 'hardcoded' tanto en UI como en respuestas de error de la API. Todo debe resolverse mediante diccionarios localizados.
6. **Documentación Completa:** XML Comments en C#, TSDoc en TypeScript, Swagger actualizado, y un ADR registrado si se tomó una decisión arquitectónica o matemática relevante.
7. **Responsividad y Sistema Visual Obligatorio:** En cualquier desarrollo futuro de frontend, el agente debe obligatoriamente verificar que la vista sea 100% responsiva y utilice el sistema de botones estandarizado antes de dar la tarea por terminada.

## 4. Flujo Git y Commits
- Prefijos de commits convencionales: `feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`, `perf:`.
- Trabajo exclusivo en ramas (`feat/*`, `fix/*`, `task/*`), nunca directo en `main`.

## 5. Verificación Obligatoria de Pipelines y Actions Pre-Commit
Antes de armar cualquier commit o preparar un Pull Request, es **estrictamente obligatorio** ejecutar y verificar localmente que pasen todos los pipelines equivalentes a GitHub Actions (`.github/workflows/ci.yml`):
1. **Backend Build & Tests:**
   `dotnet test Sparnarok.slnx --configuration Release` (debe pasar el 100% de los tests unitarios y de integración sin fallos de inicio en Hubs de SignalR ni dependencias rotas).
2. **Frontend Build, Unit Tests & Stylelint:**
   En `src/frontend/sparnarok-web`: `npm test`, `npm run lint:css` y `npm run build` (cero errores de compilación TypeScript, cero fallos de Stylelint y todos los tests de Vitest en verde).
3. **End-to-End Tests:**
   En `tests/e2e`: `npx playwright test` (todos los specs de Playwright deben estar pasando).
4. **Prohibición de Commits con Fallos:**
   Queda terminantemente prohibido generar un commit si alguno de los checks anteriores falla. Si un pipeline falla en CI, el agente o desarrollador debe reproducir localmente la suite completa de los pipelines, corregir la causa raíz y revalidar antes de armar el commit.

## 6. Reglas de Diseño Frontend, Responsividad y Sistema Visual (D&D Beyond Standard)
Para garantizar una experiencia de usuario consistente, accesible y de alta gama inspirada en D&D Beyond:
1. **Responsividad Total (Mobile-First / Fluid Design):**
   - Todo componente, vista, tabla y modal debe ser completamente funcional y responsivo en:
     - **Móvil (`< 640px`)**: Colapso a 1 columna en grillas de criaturas y configuración del simulador; flex-wrap ordenado en barras de navegación y controles de combate.
     - **Tablet (`640px - 1024px`)**: Adaptación a 2 columnas.
     - **Escritorio (`> 1024px`)**: Grid completo y layouts horizontales.
   - **Cero Desbordamientos Horizontales:** Queda estrictamente prohibido el overflow o scroll horizontal no deseado. Toda tabla de datos o de turnos (Tracker de Combate) debe estar obligatoriamente encapsulada en `.combatants-table-container` con `overflow-x: auto; -webkit-overflow-scrolling: touch;` y un `min-width` adecuado en la tabla.
2. **Sistema Canónico de Botones (`.btn`):**
   - Queda prohibido crear clases de botón fragmentadas o aisladas (`.my-custom-btn`, estilos en línea ad-hoc).
   - Todo botón debe usar la jerarquía canónica:
     - `.btn.btn-primary`: Acción principal destacada (Rojo D&D Beyond `#bc252c`).
     - `.btn.btn-secondary`: Acciones secundarias o cancelaciones (Pizarra Carbón `#1e2832`).
     - `.btn.btn-danger`: Acciones destructivas o irreversibles (Carmesí `#ff8585` / `#bc252c`).
     - `.btn.btn-gold`: Destacados de botín/tesoro o llamada a la acción especial (Oro pergamino `#c9a050`).
     - `.btn.btn-outline`: Acciones neutras con borde sutil.
     - Modificadores de tamaño: `.btn-xs`, `.btn-sm`, `.btn-lg`, `.btn-icon`, `.btn-block`.
   - **Accesibilidad y Estados:** Todo botón debe tener definidos sus estados `:hover`, `:active`, `:disabled` y `:focus-visible` (halo dorado accesible para navegación por teclado).
3. **Flujo Lógico y Posicionamiento:**
   - En modales y formularios (`.modal-actions`, `.form-actions-footer`), los botones de cancelación o secundarios deben ubicarse a la izquierda, y los botones primarios o de confirmación a la derecha. En pantallas móviles deben colapsar ordenadamente (`flex-direction: column-reverse`) priorizando el botón de acción principal.
4. **Barrera de Calidad en Pre-Commit:**
   - Todo archivo CSS debe validar contra `.stylelintrc.json` mediante `lint-staged` y `husky`. Si se rompe una regla de sintaxis o media query, el commit queda automáticamente bloqueado.
